# 007 · Choose the stack

**Date** 2026-08-18
**Type** decision
**Refs** ISS-11, ISS-12

## What

Settled the stack and recorded it in `wiki/decisions/stack.md`:

- **Backend** Python — FastAPI + uvicorn + `pyserial`, `venv` + `requirements.txt`
- **Transport** WebSocket for live frames, REST for history and the EJECT command
- **Frontend** React + Vite
- **Charts** uPlot (proposed)
- **Parsed store** SQLite, single flat table
- **Raw log** append-only text, flushed before parsing

## Why

The team is strongest in Python. At 1 Hz and 17 fields per packet, performance is irrelevant —
roughly 1,800 packets in a 30-minute flight — so the choice was made on **field reliability** and
**maintainability** instead.

The deciding factor was process count. v1 required an MQTT broker, Node-RED and a Python bridge
all running before a single byte flowed. The chosen shape is one process: the backend owns the
serial port, writes both logs, and serves the built frontend.

Rejected: Node (`serialport` is a native module needing Windows build tools), browser-only Web
Serial (manual click-through every run; a closed tab kills logging mid-flight), and Tauri (a Rust
toolchain to maintain for 1 Hz of CSV).

## Result

The parsed store is a **deliberate correction of v1**. Its four-table schema needed a
`last_insert_rowid()` round-trip plus three inserts per packet, and the cost is visible in the
data: 256 readings with no IMU/GPS row, 989 with no signal row, 6 `reading_id`s with duplicated
children. One flat INSERT makes all three failures structurally impossible.

Two issues raised by the choice:

- **ISS-11** — offline map tiles. No internet at the launch site means a default Leaflet basemap
  renders blank. The GPS panel can be built against a plain XY trace and gain a basemap later,
  so it blocks nothing.
- **ISS-12** — field laptop provisioning. Python installed, dependencies installed, frontend
  **already built**, and the USB serial driver present, all before leaving. This is the accepted
  cost of the Python + browser choice.

Also noted for the UI: EJECT fires a parachute, so it needs an armed state or confirmation, and
must distinguish *command sent* from *command acted on* — the link has no acknowledgement, so
confirmation only arrives indirectly via `CHUTE:1` in later telemetry.
